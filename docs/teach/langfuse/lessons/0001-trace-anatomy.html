Trace Anatomy

Lesson 1 · 2026-08-03 · ~10 minutes

A trace is a recording of a single session — one user request, one agent turn, one conversation. If you've ever used OpenTelemetry, Datadog APM, or Sentry, the concept is the same: a trace captures everything that happened, in order, with timing.

In Langfuse, a trace is the top-level container. Inside it lives a tree of observations — the individual events that made up the session. Every LLM call, every tool execution, every step is an observation.

Observation Types

Langfuse has four observation types. You only need to worry about two of them right now:

Type What it represents Example
GENERATION An LLM call — request in, response out Asking Claude to write code
SPAN Any other operation — tool call, database query, step Running bash, read, edit
EVENT An instantaneous occurrence (rare) Log line, metric snapshot
LLM_USAGE Token/cost data (usually merged into GENERATION) —
Key insight A trace is a timeline. Each observation has a startTime and endTime. You can see exactly how long each step took, what was sent, and what came back.

How the pi extension builds traces

The pi extension at .pi/extensions/langfuse-tracing.ts creates one trace per agent session. For each user turn, it emits:

  1. GENERATION — the LLM request (system prompt + messages) and response
  2. SPAN — for every tool call (bash, read, edit, write)
  3. GENERATION — the next LLM request (with tool results fed back in)
  4. …and so on, until the agent settles

The result is a tree: generations are the "thinking" steps, and the spans under them are the "doing" steps.

Read the pattern Each turn is GENERATION → SPAN → GENERATION → SPAN → … The LLM thinks, then acts (tool call), then the tool result feeds back into the next LLM call. This is the agent loop, captured in real time.

What each generation contains

Here's what a generation observation actually stores. This is the first LLM call in the trace:

INPUT (system prompt + messages):
  [
    {"role": "system", "content": "You are an expert coding assistant..."
      "(the full pi system prompt)"},
    {"role": "user", "content": "WHATS happening"}
  ]

OUTPUT (model response):
  [{"type": "thinking", "thinking": "Open Notebook is up and running..."},
   {"type": "text", "text": "Open Notebook is fully up and running..."}]

USAGE:
  input: 14,000 tokens
  output: 244 tokens
  total: 0 (not used)

COST:
  totalCost: 0.000963424

Every generation captures the full input sent to the model (including the system prompt) and the full output returned. This is what makes Langfuse powerful for debugging — you can replay exactly what the agent saw.

What this enables

With this level of data captured for every session, you can answer questions like:

  • How many tokens does a typical session consume?
  • Which tool calls take the longest?
  • How many turns does the agent need before it settles?
  • Did the agent's final output actually answer the user's question?

That last question is where evals come in — and that's Lesson 2.

Exercise: inspect a trace yourself

Pick any trace from the running instance. Open a terminal and try:

source .env.langfuse

# List recent traces
curl -H "Authorization: Basic $(echo -n "$LANGFUSE_PUBLIC_KEY:$LANGFUSE_SECRET_KEY" | base64 -w0)" \
  "http://localhost:3000/api/public/traces?limit=3" | python3 -m json.tool

# Get observations for a trace
curl -H "Authorization: Basic $(echo -n "$LANGFUSE_PUBLIC_KEY:$LANGFUSE_SECRET_KEY" | base64 -w0)" \
  "http://localhost:3000/api/public/observations?traceId=<TRACE_ID>&limit=30" | python3 -m json.tool

Look at the pattern: how many generations? How many spans? What's the longest step?
